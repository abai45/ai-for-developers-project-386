# 2. Design-First: TypeSpec → OpenAPI → SDK, двойная генерация артефактов

- Статус: принято (31.10.2026)
- Тикеты: #7, #10, #11, #13; полный текст: `docs/decisions.md` («Контракт…», «Контрактная цепочка…»)

## Контекст
Фронтенд и бэкенд должны говорить по одному контракту; расхождение контракта и кода — главный источник дефектов в fullstack-проекте без тестового покрытия API.

## Решение
Единственный источник истины API — TypeSpec в `docs/spec/tsp/`. Из него одной командой `mise run spec` генерируются: `docs/openapi.json` (OpenAPI 3.1, коммитится), TS-типы `frontend/src/lib/api/schema.d.ts` (коммитятся), поверх — рукописный типизированный клиент (`lib/api/client.ts`, openapi-fetch). Бэкенд: openapi-generator (spring, interfaceOnly) на `generate-sources` создаёт интерфейсы контроллеров и DTO (`target/generated-api`, не коммитится); логика пишется вручную в подпакетах `controller/service/store/validation`. Дрейф-чек `mise run spec-check` — первый шаг `mise run check` и CI: перегенерация не должна менять закоммиченные артефакты. Порядок правок API: TypeSpec → генерация → код обеих сторон. Идентификаторы контракта на английском, `@doc` и UI — на русском.

## Последствия
- Ручные правки сгенерированных файлов запрещены (AGENTS.md); CI ловит дрейф, включая новые незакоммиченные файлы.
- Ответы живого сервера совпадают с контрактом по путям/кодам/телам — это проверяется API-тестами через HTTP-шов.
