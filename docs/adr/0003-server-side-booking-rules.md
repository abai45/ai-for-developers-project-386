# 3. Правила бронирования выполняет сервер; проверка пересечения атомарна

- Статус: принято (31.10.2026)
- Тикеты: #10, #11, #12; спецификация #6 («Правила расписания»); полный текст: `docs/decisions.md`

## Контекст
Запрет двойного бронирования, проверенный только в UI, обходится любым другим клиентом прямым запросом к API.

## Решение
Сервер — источник истины расписания: рабочее время 09:30–18:00 Asia/Almaty ежедневно; окно записи — 14 календарных дней со следующего дня; старты слотов `09:30 + k × шаг типа`, пока `старт + длительность ≤ 18:00`; длительность слота равна длительности типа. `POST /api/meetings` принимает только время, являющееся стартом слота выбранного типа (иначе `400 errors[]`). Пересечение интервалов запрещено строго (касание окончание=начало разрешено) и **между разными типами тоже**; проверка и создание атомарны под монитором in-memory хранилища. Статусы слотов (`free|occupied`) выдаёт сервер по фактическим встречам; клиент не дублирует правила — окно календаря на фронте строится из ответа сервера.

## Последствия
- Проверки на фронте (native-атрибуты) — только эргономика, не защита.
- Конкурентная запись одного слота даёт ровно один `201`, остальные `409` (тест с 5 потоками).
